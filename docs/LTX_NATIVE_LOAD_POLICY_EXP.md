# LTX 原生加载策略：显式一致流式模式（EXP）

新增两个独立节点：`LTX · Native Load Policy` 和 `LTX · Observe Native Load Policy`。它们不采样、不替换 LoRA、不改 sigma 或音轨。

`legacy_default` 是默认选项：原 MODEL 对象原样返回，旧工作流无需添加节点或迁移。显式选择 `consistent_streaming_exp` 才克隆 MODEL，保留已有包装器，并在原生采样准备阶段委托 Core 的 `force_offload=True`。

接线放在原 LTX Setup 的 MODEL 输出之后、EAV／Relay 和 Guider 之前；Stage Bind／Audit 也使用同一最终 MODEL。Observe 同时连接最终 MODEL、实际候选 LATENT 和策略节点的 runtime，可检查准备委托次数及包装器是否还在。它的报告不是采样完成、可移植缓存、候选来源或质量证书。

## 为什么需要显式选项

在当前 Core／LoRA 组合中，部分模块驻留与流式补丁走不同计算和舍入路径。已有失败链的 full／cold 输入完全一致，但实际首次 denoiser 输出不同；原失败保留。固定原输入、三步、LoRA 和后端，仅改为 Core 一致流式准备的独立对照恢复了同值。

这不是要求所有用户开启的新默认。显式模式可能改变相对旧混合驻留方式的数值；不承诺与旧结果逐位一致、任何机器都可复现或普遍更快。第三方包装器继续委托，可能覆盖该请求；检查实际报告，而不是仅看节点存在。

## 已完成的本地验收

公开节点在原生 Chromium 画布完成一条 Identity＋外置 EAV／Relay full→全新进程冷读取链：每侧原三步，121 帧、24 fps、1024×576、约 5.04 秒，完整 H.264＋AAC 严格解码。两侧候选 latent 与全部解码 RGB／PCM 精确一致，音轨与对应原片完全相同。121 帧是原既有 `trim_to_8n_plus_1` 对 124 帧源的裁尾，不是本次改变时间轴。

实际 EAV 为 `apply_exp`／tau4，48 视频块各三次施加，最大增益约 1.10954，原硬限 1.5 保持；Relay 同时实际施加，后端委托 720 次。策略每侧实际准备委托一次。六份原选定模型、存档、源视频、Core／控制器和公共源码前后完整性均通过；旧 LoRA 强度 0.8 不变。

相关 195 项 CPU 回归通过；四图交付后，包含原双模型接缝范围的当前 18 范围回归共 305 项通过，CUDA 未初始化，冻结源码未改变。旧 577 个节点的顺序、schema、节点实现和 2100 个旧 JSON 未变，仅追加两节点和四张独立新图。注册入口的严格源码变更报告仍保留，另以三个精确追加片段重构原入口 SHA 完成独立审查。

四张新增图已在原生画布可见编辑加载模式、外置 EAV 和局部 Relay 提示词，并实际另存、刷新、重开；具名连线和控件保真均通过，全程队列／history 为空。首轮严格保存审计因两处已连接报告输入的空显示控件停止，原失败保留；复验复用已有精确两字段校验，非忽略未知字段或更改执行输入。编辑测试不继承为四预设全部成片或质量资格。

该结果是一条配置的机械验收，不是普通／Identity 所有素材、第三方后端、长时长、视觉听觉质量或全部双采完成，也尚未发布。当前环境提示 comfy-kitchen 0.2.35 低于 Core 推荐 0.2.36；本次未升级用户共享环境。

新增工作流单独放在 `examples/workflows/60-ltx-rgb-stage-split/native-load-policy-exp/`。EAV／Relay 仍保留原 `report_only` 示例默认；需要实际效果时显式选择 `apply_exp`。冷图必须填入同一任务刚保存的输入 manifest 和 SHA；它恢复输入后仍重新运行原三步，不是复用已完成采样缓存。完整人工看听和其他路线的收尾另列。
