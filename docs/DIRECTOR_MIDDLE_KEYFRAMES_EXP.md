# 导演台中间关键帧

中间关键帧用于指定一张图片在镜头内部的出现位置，复用现有 H3 多关键帧条件构建器，不是把图片逐张剪成幻灯片。
普通提示词可以直接使用；Prompt Relay 只在显式开启时参与，不是必需依赖。

## 在导演台设置

1. 点击“画面来源”。普通镜头选择首尾模式并添加首帧、尾帧；原音驱动使用首帧模式和已上传录音，可直接添加中间图，不需要虚构尾帧。其它缺少端点的普通路线仍提示补全，不自动猜图。
2. 展开“中间关键帧”，添加条目。可以选择素材库已有图片，或在对应条目上传图片；不自动把图片改成全片参考。
3. 为每项选择百分比、秒或帧号，并填写位置。帧号从 0 开始，使用 24fps；中间帧不能与端点或另一项重叠。
4. 默认按“最终可见片段”定位。修改时长后，秒数和帧号保持原值，百分比重新计算；越界时保留原请求并提示修正，不自动移动图片。
5. 可以单独停用条目，保留图片和位置草稿。删除条目或素材引用可以撤销，不删除电脑原文件。

“图像处理”高级区可设置每项原始混噪值和缩放方式。默认值 0.999 沿用原多关键帧节点，**不是相似度百分比**。
居中裁剪与拉伸只作用于实际送模图片；界面预览始终完整等比显示。大量图片会增加编码时间和显存占用，没有人为设置七张中间图的硬上限。

复制镜头会创建新的条目 ID，但继续引用原图片。重连图片会同步所有相关镜头的条目；撤销恢复旧引用，旧图片文件不被覆盖。
上传期间切换项目、删除条目或替换该图片时，迟到结果不会覆盖新编辑；切换镜头但仍在同一工程时，结果只绑定发起上传的原镜头、原条目。

## 两种时间轴

H3 的生成帧轴需要对齐 `17n+5`；最终交付片段可能裁去补齐的尾部。
例如 4 秒、24fps 最终交付 96 帧，生成帧轴为 107 帧。95% 在默认可见时轴上定位到帧 90；
显式选择完整生成时轴时定位到帧 101，这一帧在最终裁片外，会提示提醒。

帧号和秒数表示绝对位置，百分比按所选时轴的最后一帧计算，并按半帧向上取整。
它们不是改变镜头时长、生成步数或音频速度的控件。旧首尾帧和已有交付裁剪规则保持不变。

## 高级画布接线

新增 `H3 中间关键帧条件 · 可选 Relay (EXP/T8)`，节点 ID 为 `MiniMaxH3DirectorKeyframeConditioningEXPT8`。
图片计划仍由原 `MiniMaxH3KeyframePlanT8Advanced` 节点按顺序追加；其原有接口和默认时间轴含义不变。

| 输出槽 | 内容 | 接法 |
| --- | --- | --- |
| 0 | MODEL | 接采样设置或引导器的 MODEL，与同节点 positive 成对使用 |
| 1 | positive | 接引导器条件；需要语义桥接时沿原桥接路线使用 |
| 2 | av_latent | 接当前阶段的采样 LATENT |
| 3 | mux_audio | 沿原最终音频连接，不把报告文字接到音频口 |
| 4 | conditioned_prompt | 查看实际素材标签替换后的提示词 |
| 5 | media_map_json | 查看图片编号及素材身份 |
| 6 | report_json | 查看关键帧位置、独立混噪和实际安装状态 |

不连接 Relay Plan 时走普通条件构建；连接后，Plan 的文字和长度生效。
Relay 使用同一次新图像编码产生的 token 和实际物理位置布局，不先编码普通条件再修改旧 embedding。
不要只取新 positive，却继续使用没有对应位置补丁的旧 MODEL。

标准低分辨率加高清双采分别按 LOW/HIGH 实际画布重新编码原图片，阶段 MODEL 保留各自 LoRA 顺序和强度。
既有 learned 3D latent upscaler、步数、sigma、音频和续镜方案不因添加中间图而改变。
未知外部 forward 保留并继续执行；若独立混噪补丁无法安装，报告会明确未应用，不把普通生成返回冒充优化成功。

## 兼容与验收范围

旧工程没有中间关键帧字段时继续原路线。新版页面提交启用中间图的任务前检查服务端协议，旧 Core 未确认时不会静默忽略条目继续生成。
先保存工程，等待已有任务结束后再更新并重启 Core；页面不会替用户自动重启服务。

当前已验证真实微型 Core、视频 Encoder、普通与 Relay 的两步 CPU 采样、8 张中间图实际消费、实际位置布局配对、
标准双采编译接线，以及独立浏览器中的编辑、下载工程 JSON、复制、撤销、素材删除和上传迟到隔离。
文字编码器是明确标注的合成测试夹具；这不是完整训练模型的画质或 GPU 验收。

HyperFlow 五种配方已接入独立阶段的条件工厂、LOW 原图准备及实际 HIGH 画布。连续双采保存原素材、mask 与原 prepared noise，不重新抽噪声。原音首帧加中间图已有真实 tiny Core／视频 Encoder 的普通与 Relay 采样检查；文字、适配器与音频编码器为明确合成夹具。
自有中间图补丁已通过精确身份检查及同版本新进程仅 TAIL 恢复，包含普通／Relay、独立混噪和原音遮罩。检查只使用 MODEL 副本，不清除用户补丁；未知外部执行对象保留执行，但不冒充已认证的跨进程缓存。另已实际运行经过完整 learned 3D 的 HyperFlow 8+4／partial 4+4 两阶段 CPU 链；这仍不是训练底模的 GPU 画质验收。具体路线及原音恢复的来源提示见 [HyperFlow 组合范围](HYPERFLOW_DIRECTOR_COMBINATION_AUDIT.md)。
2026-10-22 的 HyperFlow 中间图 OFF／ON 隔离训练模型对照，已实际观察原图编码、模型空间位置投影与每次前向的关键帧消费，网络进度到 8；两片全部 240 帧、1024×576、24fps 及原生音轨／PTS／strict 通过，见本地 `h22-D-HF-media-v1/actual-v1/collection.json`。另完成中间图叠加区域裁剪的原生 8、标准 4+4、HyperFlow 连续 4+4 三片完整 360 帧控制审计，见 `h22-C-middle-batch-closed-v1.json`；后者主要证明控制残差与裁剪消费，不替代独立关键帧位置观察。

同日，带中间图及区域裁剪的固定 HEAD 另经新进程 Load0＋TAIL4 实际恢复，完整 120 帧音视频及原始 AV／控制／停止证据通过，MP4 与原热续采片字节相同，见 `h22-cold-tail-postflight-v2/actual-v1/collection.json`。这证明该固定输入的冷恢复兼容，不替代独立位置消费观察，也不宣称没有保存的热执行最终 raw latent 与冷执行逐位相同。
